Персональный блог бэкенд-разработчика

    Guardian: управляемый шлюз для безопасного исходящего HTTP(S)-трафика

    September 20, 2026 · akozadaev

    Введение#

    Современное приложение редко работает изолированно. Оно обращается к платёжным системам, облачным API, партнёрским сервисам, репозиториям пакетов и множеству других внешних ресурсов. Чем больше таких связей, тем труднее ответить на простые, но важные вопросы: какой сервис имеет право обращаться к конкретному адресу, кто отправляет слишком много запросов, можно ли оперативно заблокировать опасный домен и не используется ли сервер для доступа к внутренней сети через SSRF-уязвимость.

    Guardian - написанный на Go forward-прокси для централизованного контроля исходящего HTTP- и HTTPS-трафика. Клиенты направляют запросы не напрямую во внешнюю сеть, а через Guardian. Прокси применяет политики доступа, проверяет пользователя, ограничивает нагрузку, блокирует опасные назначения и передаёт разрешённый запрос целевому серверу. Управление правилами выполняется через REST API, состояние хранится в PostgreSQL, а метрики доступны Prometheus.

    Guardian занимает место между простым сетевым межсетевым экраном и тяжёлым коммерческим Secure Web Gateway. Это не замена reverse-proxy вроде Nginx: reverse-proxy публикует собственные приложения для входящего трафика, тогда как Guardian контролирует исходящие обращения клиентов и сервисов.

    Почему проект практически значим#

    Обычный сетевой firewall хорошо оперирует IP-адресами и портами, но HTTP-политике часто нужен прикладной контекст: метод, URL, путь, заголовок, размер тела, роль пользователя. Если такие проверки реализуются отдельно в каждом микросервисе, правила расходятся, их трудно менять и практически невозможно централизованно наблюдать.

    Guardian выносит эту задачу в единую точку контроля и может быть полезен в нескольких сценариях:

    • ограничение доступа микросервисов и служебных программ к внешним API;
    • блокировка запросов к localhost, частным сетям и адресам облачных metadata-сервисов при эксплуатации SSRF;
    • применение единых allow/block-политик без выпуска новой версии клиентского приложения;
    • защита внешних API и самого прокси от всплесков нагрузки с помощью квот на IP и пользователя;
    • интеграция административного доступа с JWT или корпоративным OAuth2/IdP;
    • наблюдение за числом запросов, задержками, объёмом трафика, активными соединениями и срабатываниями правил;
    • построение собственного расширяемого outbound-шлюза в инфраструктуре организации без привязки к SaaS-поставщику.

    Например, можно разрешить сервису только GET к API партнёра, заблокировать отправку больших тел, запретить обращения из определённой сети или вернуть специальный ответ при совпадении с политикой. Правило меняется через Admin API и затем попадает на работающие экземпляры прокси без ручной правки их конфигурации.

    Назначение и возможности#

    Guardian принимает proxy-трафик на порту 8080. Обычные HTTP-запросы он пересылает на целевой сервер, предварительно проверив их и удалив служебные hop-by-hop заголовки. Для HTTPS используется метод CONNECT: после проверки назначения Guardian создаёт двунаправленный TCP-туннель между клиентом и сервером.

    У проекта три раздельных интерфейса:

    ПортНазначение
    8080HTTP forward-proxy и HTTPS CONNECT
    8081Admin API, /health, /ready
    9090метрики Prometheus и проверка состояния

    Разделение портов упрощает сетевую политику: клиентам можно открыть только прокси, администраторам - Admin API, а Prometheus - endpoint метрик.

    Основные функции Guardian:

    • действия правил allow, block и modify;
    • условия по методу, URL, пути, query string, host, IP, заголовкам, content type, телу и его размеру, идентификатору и роли пользователя;
    • логические деревья условий AND, OR, NOT;
    • сравнения eq, neq, in, not_in, contains, prefix, regex, gt, lt, exists, включая CIDR для IP;
    • локальный JWT HS256, RBAC и интеграция с OAuth2 через introspection либо JWKS;
    • ограничение RPS на IP и пользователя, а также числа одновременных соединений с одного IP;
    • PostgreSQL для правил, пользователей, аудита и опционального журнала запросов;
    • Redis для общего кэша, отзыва и кэширования токенов, правил, rate-limit-счётчиков и опциональных ответов;
    • опциональная асинхронная публикация событий в Kafka;
    • метрики Prometheus, health/readiness endpoints и корректное завершение процесса.

    Полный административный контракт описан в OpenAPI, а практические команды - в инструкции.

    Как проходит запрос#

    Горячий путь запроса построен как последовательность дешёвых проверок перед более дорогим сетевым обращением:

    1. Guardian определяет IP клиента. Заголовки X-Forwarded-For и X-Real-IP принимаются во внимание только от адресов из server.trusted_proxies, поэтому клиент не может произвольно подменить IP.
    2. Счётчик соединений проверяет лимит для IP, затем rate limiter проверяет частоту запросов.
    3. Если передан токен, он валидируется; при обязательной аутентификации отсутствие или ошибка токена приводят к отказу. Из claims извлекаются роль и персональная квота.
    4. Filter Engine строит контекст запроса и последовательно проверяет активные правила.
    5. При block формируется локальный ответ, при modify изменяются заголовки запроса или тело ответа, при allow обработка продолжается.
    6. Проверяется адрес назначения. При выключенном allow_private_targets блокируются loopback, link-local, RFC1918, CGNAT, IPv6 ULA, .local, localhost и адреса metadata-сервисов. Ошибка DNS трактуется безопасно - как запрет.
    7. HTTP-запрос пересылается upstream-серверу либо создаётся CONNECT-туннель.
    8. Обновляются метрики; журнальное событие асинхронно отправляется в Kafka и, если явно включено, сохраняется в PostgreSQL.

    Такой порядок снижает бесполезную нагрузку: заведомо запрещённый или превысивший квоту запрос не занимает upstream-соединение.

    Алгоритмы фильтрации#

    Правила хранятся как дерево условий. Внутренний узел задаёт AND, OR или NOT, а лист - поле, оператор сравнения и значение. Это позволяет представить как простую проверку method == POST, так и составную политику: «заблокировать POST или PUT к заданному пути, если запрос пришёл из указанной сети и пользователь не имеет нужной роли».

    После загрузки правила стабильно сортируются по убыванию приоритета. Движок применяет стратегию first match wins: первое совпавшее включённое правило определяет действие. Если ни одно правило не совпало, запрос разрешается. Следовательно, порядок и приоритет являются частью политики безопасности, а наиболее специфичные запрещающие правила обычно должны иметь больший приоритет.

    Вычисление логического дерева использует короткое замыкание: AND прекращается при первом ложном условии, OR - при первом истинном. Регулярные выражения компилируются один раз и сохраняются в потокобезопасном кэше. Проверка IP поддерживает как точные адреса, так и CIDR-сети.

    Активный набор правил хранится в памяти и защищён sync.RWMutex: множество параллельных запросов читает его одновременно, а обновление кратковременно заменяет весь snapshot. При старте и затем с интервалом cache.rules_ttl экземпляр обновляет правила из общего хранилища. CRUD-операции инвалидируют кэш. В результате база данных не участвует в каждом запросе, а изменения распространяются между экземплярами с небольшой, управляемой задержкой.

    Аутентификация, RBAC и ограничение нагрузки#

    Guardian поддерживает роли admin, moderator, user и guest. Им соответствуют разрешения на чтение и изменение правил, управление пользователями, просмотр статистики и использование прокси. Локальная выдача JWT через bootstrap endpoint предназначена для разработки; в production bootstrap следует отключить и использовать внешний IdP либо заранее организованную выдачу токенов.

    При OAuth2 возможны два режима:

    • introspection для проверки opaque-токена на стороне IdP;
    • локальная проверка подписанного JWT по RSA-ключам из JWKS, которые кэшируются.

    Результат проверки токена сохраняется с TTL, поэтому внешний IdP не вызывается на каждый запрос. Прокси также удаляет Authorization и Proxy-Authorization перед отправкой upstream, не раскрывая учётные данные клиента целевому сайту.

    При доступном Redis rate limit реализован общим секундным счётчиком, атомарно увеличиваемым Lua-скриптом. Это даёт согласованную квоту для нескольких экземпляров Guardian. Если Redis недоступен, система продолжает работу с локальным token bucket из golang.org/x/time/rate; такой fallback повышает доступность, но лимит в этом случае действует отдельно на каждом экземпляре. Лимит одновременных соединений также локален для процесса. Эти особенности нужно учитывать при расчёте кластерных квот.

    Защита от SSRF и границы HTTPS-фильтрации#

    До соединения с upstream Guardian разрешает имя через DNS и отклоняет цель, если хотя бы один полученный адрес относится к локальному или частному диапазону. Проверка применяется и к обычному HTTP, и к CONNECT. Это защищает, например, от попытки обратиться через прокси к 127.0.0.1, внутренней базе данных или 169.254.169.254.

    При этом текущая реализация CONNECT не выполняет TLS-interception (MITM). Содержимое HTTPS остаётся зашифрованным от клиента до целевого сервера. Guardian может проверить пользователя, IP, метод CONNECT и адрес host:port, ограничить соединение и объём трафика, но не видит путь, HTTP-заголовки и тело внутри туннеля. Это осознанная граница: сохраняется сквозное TLS-шифрование и не требуется устанавливать корпоративный CA, но для контентной DLP/антивирусной проверки HTTPS понадобится отдельное расширение архитектуры.

    Почему для реализации выбран Go#

    Прокси обслуживает большое количество независимых сетевых соединений, поэтому модель конкурентности Go хорошо соответствует задаче. В проекте она используется не как абстрактное преимущество языка, а в конкретных местах:

    • три сервера - proxy, admin и metrics - работают параллельно в goroutine;
    • направления CONNECT-туннеля копируются одновременно двумя goroutine, после чего WaitGroup ожидает их завершения;
    • атомарные счётчики собирают число соединений, туннелей и байтов без тяжёлой блокировки горячего пути;
    • sync.RWMutex позволяет параллельно читать snapshot правил, а sync.Map используется для кэша регулярных выражений и limiter-объектов;
    • context.Context ограничивает время подключения к инфраструктуре, запросы к БД и graceful shutdown;
    • defer гарантирует освобождение соединений, буферов и счётчиков на всех ветвях обработки;
    • интерфейсы отделяют кэш, внешний валидатор токенов и publisher событий, упрощая тестирование и замену реализаций.

    Для HTTP-ядра применяется fasthttp. Запросы и ответы берутся из pool и возвращаются после обработки, настроены пул соединений к upstream, DNS-кэш, тайм-ауты и максимальное число соединений на host. CONNECT копирует данные через переиспользуемый буфер заданного размера. Такой подход уменьшает число аллокаций и нагрузку на garbage collector.

    Статическая типизация Go полезна для security-проекта: роли, действия и операторы представлены отдельными типами и константами, а ошибки явно передаются вызывающему коду. Сборка с CGO_ENABLED=0 создаёт самостоятельный бинарный файл, благодаря чему production-образ состоит из минимальной Alpine-системы, сертификатов, часовых поясов и приложения.

    Одновременно Go требует дисциплины. Goroutine не должна запускаться бесконтрольно; общие структуры обязаны быть защищены mutex или atomic; тело запроса нельзя удерживать после возврата pooled-объекта; сетевые операции нуждаются в тайм-аутах; фоновые задачи должны завершаться вместе с приложением. В Guardian эти требования отражены в пулах, лимитах соединений, контекстах и обработке SIGINT/SIGTERM.

    Наблюдаемость и эксплуатация#

    Guardian экспортирует счётчики запросов по методу и статусу, histogram задержек, активные соединения и CONNECT-туннели, входящие и исходящие байты, число блокировок и срабатывания каждого правила. На их основе можно строить алерты на рост 429/5xx, заполнение соединений, увеличение p95/p99 и резкие изменения объёма трафика.

    /health сообщает, что процесс работает, а /ready - что экземпляр готов принимать нагрузку. Kubernetes использует их как liveness/readiness probes, а HAProxy проверяет /ready на административном порту и перестаёт направлять трафик в неготовый экземпляр.

    Синхронная запись каждого запроса в PostgreSQL по умолчанию выключена, поскольку она превратила бы БД в узкое место горячего пути. Для большого потока предпочтительна Kafka с последующей обработкой consumer-приложением. Response cache также выключен по умолчанию и, если включён, применяется только к анонимным GET без Cookie и Authorization, когда ответ явно содержит Cache-Control: public и не содержит Set-Cookie или Vary.

    Варианты развёртывания#

    Локальный бинарник#

    Для разработки достаточно поднять PostgreSQL и Redis через Compose, задать сильный JWT secret и запустить приложение:

    docker compose up -d postgres redis
export GUARDIAN_AUTH_JWT_SECRET="$(openssl rand -hex 32)"
go mod download
make run

    Для production бинарник можно запускать под systemd. Перед ним желательно разместить L4/L7-балансировщик, закрыть Admin API сетевой политикой и отдельно настроить сбор метрик. Миграции БД должны выполняться отдельным контролируемым шагом релиза.

    Docker Compose#

    Полный демонстрационный стенд запускается командой:

    docker compose up -d --build

    Он включает Guardian, PostgreSQL и Redis. Kafka и связка Prometheus/Grafana включаются профилями:

    docker compose --profile kafka --profile monitoring up -d --build

    Compose удобен для разработки, интеграционных тестов и небольшого односерверного контура. Значения паролей и bootstrap token из примера являются локальными и должны быть заменены перед любым внешним развёртыванием.

    Kubernetes#

    В deployment manifest - deploy/k8s/deployment.yaml (его сейчас нет в репозитории, да и негде мне сейчас развернуть) три реплики Guardian, ClusterIP Service, probes, resource requests/limits и HPA от 3 до 10 pod при средней загрузке CPU 70%. Образ приложения не хранит состояние, поэтому pod можно безопасно пересоздавать, а трафик распределять между готовыми репликами:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: guardian-proxy
  labels:
    app: guardian
spec:
  replicas: 3
  selector:
    matchLabels:
      app: guardian
  template:
    metadata:
      labels:
        app: guardian
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "9090"
        prometheus.io/path: "/metrics"
    spec:
      containers:
        - name: proxy
          image: guardian:latest
          imagePullPolicy: IfNotPresent
          ports:
            - name: proxy
              containerPort: 8080
            - name: admin
              containerPort: 8081
            - name: metrics
              containerPort: 9090
          env:
            - name: GUARDIAN_POSTGRES_DSN
              valueFrom:
                secretKeyRef:
                  name: guardian-secrets
                  key: postgres-dsn
            - name: GUARDIAN_REDIS_ADDR
              value: "redis:6379"
            - name: GUARDIAN_AUTH_JWT_SECRET
              valueFrom:
                secretKeyRef:
                  name: guardian-secrets
                  key: jwt-secret
            - name: GUARDIAN_PROXY_ALLOW_PRIVATE_TARGETS
              value: "false"
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              cpu: "4"
              memory: "2Gi"
          readinessProbe:
            httpGet:
              path: /ready
              port: admin
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health
              port: admin
            initialDelaySeconds: 5
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: guardian-proxy
spec:
  selector:
    app: guardian
  ports:
    - name: proxy
      port: 8080
      targetPort: proxy

      targetPort: admin

      port: 9090

apiVersion: autoscaling/v2

    • управляемый PostgreSQL с резервным копированием и, при необходимости, read replica;
    • отказоустойчивый Redis, если нужны общие rate limits и кэш между pod;
    • Secret/External Secrets для DSN, JWT и OAuth2-параметров;
    • NetworkPolicy: клиентам разрешён 8080, администраторам 8081, Prometheus 9090;
    • PodDisruptionBudget, anti-affinity или topology spread constraints;
    • ServiceMonitor либо scrape annotations для Prometheus;
    • egress NetworkPolicy, допускающую pod только к разрешённой инфраструктуре и внешней сети;
    • отдельный Job миграции схемы перед обновлением Deployment.

    RollingUpdate подходит для Guardian, поскольку пользовательские сессии не хранятся в процессе. Однако длительный CONNECT-туннель привязан к конкретному pod до закрытия соединения. При обновлении нужны достаточный terminationGracePeriodSeconds, readiness drain и тайм-аут завершения, иначе такие туннели будут оборваны.

    Балансировка и горизонтальное масштабирование#

    В репозитории есть пример для балансировки можно использовать HAProxy с тремя backend-экземплярами, round-robin и проверкой /ready. Возможны три стратегии:

    • roundrobin - равномерное распределение новых запросов, хороший вариант по умолчанию;
    • leastconn - полезен при большом числе CONNECT-туннелей разной длительности;
    • source - привязка по IP, когда нужна липкость, хотя функционально Guardian её не требует.

    Для обычного HTTP балансировщик может переиспользовать соединения, а CONNECT после назначения остаётся на выбранном backend до конца туннеля. Поэтому при смешанной короткой HTTP-нагрузке и долгих туннелях leastconn часто распределяет ресурсы точнее round-robin.

    Экземпляры Guardian не хранят пользовательские сессии, но не всё состояние полностью глобально. PostgreSQL является источником правил и пользователей, Redis координирует кэш и секундные rate-limit-счётчики, а in-memory snapshot правил, conn limit и fallback token bucket принадлежат конкретному процессу. Sticky sessions для корректности не нужны; при отсутствии Redis эффективный суммарный лимит может расти пропорционально числу реплик.

    Если балансировщик добавляет XFF, его адрес или CIDR необходимо внести в server.trusted_proxies. Иначе Guardian намеренно будет считать клиентом сам балансировщик. Admin API лучше балансировать отдельным внутренним Service/route и не публиковать вместе с публичным proxy endpoint.

    Ограничения и направления развития#

    Guardian уже решает практически полезную задачу outbound-контроля, но его границы важно учитывать:

    • HTTPS CONNECT не расшифровывается, поэтому контентные правила внутри HTTPS неприменимы;
    • приоритетная модель first match wins требует аккуратного проектирования политик, а default action сейчас - allow;
    • обновление правил между экземплярами происходит не мгновенно, а при следующей перезагрузке snapshot;
    • conn limit локален, а общий rate limit зависит от доступности Redis;
    • production HA для PostgreSQL, Redis и Kafka обеспечивает инфраструктура, а не само приложение;
    • встроенный интерфейс управления - API; полноценная web-панель может быть отдельным клиентом.

    Логичными продолжениями проекта могут стать режим default deny, push-уведомления об изменении правил, категоризация доменов, policy-as-code, трассировка OpenTelemetry, полноценный audit pipeline, более точный DNS pinning/rebinding control и, при обоснованной необходимости, отдельный управляемый режим TLS inspection.

    Заключение#

    Guardian показывает, как на Go можно построить не просто сетевой ретранслятор, а управляемый компонент безопасности: с прикладными правилами, защитой от SSRF, идентификацией пользователей, квотами, наблюдаемостью и несколькими вариантами поставки. Его ценность состоит в централизации исходящей политики и в прозрачной архитектуре, которую можно разворачивать в собственном контуре и расширять под требования организации.

    Проект особенно уместен там, где простого firewall уже недостаточно, а внедрение большого коммерческого SWG избыточно. Один экземпляр подходит для разработки и небольшого контура; несколько экземпляров за HAProxy или Kubernetes Service дают горизонтальное масштабирование, а PostgreSQL и Redis обеспечивают общее состояние. При грамотной изоляции портов, внешнем IdP, отказоустойчивых хранилищах и мониторинге Guardian способен стать практической точкой контроля исходящего HTTP(S)-трафика.
